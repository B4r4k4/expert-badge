Unit Introduction

This domain carries about 21 of the 150 questions, and it contains the topic that recurs most often according to candidates' accounts: an assistant connected to a retrieval-augmented generation (RAG) system over documents that are updated periodically. This unit builds the complete engineering picture around the model: the ingestion and query pipelines, keeping the index up to date, choosing the interaction pattern for the interface, resilience patterns, structured outputs, caching, and then integration architecture, the LLM gateway, testing, observability, conversational design, agents and secure development. The questions in this domain are mostly diagnostic scenarios: a symptom the question describes, a stage responsible for it, and a specific engineering fix; the usual distractors are generic solutions such as “raise the timeout” or “retrain the model”.

Before You Start

The previous units were about the models themselves. This unit is about the software around the model: how to build a complete RAG system that stays up to date, how to serve the model through an interface that others depend on, how to make the system withstand failures, how to connect it to enterprise systems, and how to test and monitor it. It is Domain 3 (about 21 questions out of 150).

You will meet many software-engineering terms here: HTTP status codes, retries, the circuit breaker, queues and gateways. We explain each one with an everyday analogy, and you need no programming background.

Before this you need from Unit 00: Sections 4.5 and 4.6 (vector representations and RAG) and Sections 5.1 and 5.3 (the server, the interface and caching). From Unit 03: Section 3.5 (ranking metrics).

Learning Outcomes

By the end of this unit, you will be able to:

  • Draw an end-to-end RAG pipeline with its two stages (ingestion and query) and identify the key decision in each component.
  • Diagnose the symptoms of stale or incorrect RAG and link each symptom to its root cause and its correct fix.
  • Choose the interaction pattern, protocol and HTTP status code appropriate to each case in model-serving services.
  • Apply resilience and security patterns to LLM APIs: retry with backoff, idempotency keys, circuit breakers, quotas and versioning.
  • Distinguish architectural integration patterns and determine when an LLM gateway or a separate service is the answer.
  • Design a testing and observability strategy for non-deterministic, model-dependent software.
  • Apply the principles of reliable agents, conversational AI and secure development when integrating AI into enterprise systems.

Chapter 1

RAG Architecture and Keeping It Up to Date

1.1 End-to-End RAG Architecture

In Plain Terms

A RAG system has two separate pipelines that run at different times. The ingestion pipeline runs in advance (or whenever a document changes): it reads the documents, cuts them into chunks, adds information about each chunk, converts the chunks into vectors, and saves them in the index. The query pipeline runs with every question: it understands the question, searches the index, ranks the results, sends the best of them to the model together with the question, and then returns the answer with its sources.

Understanding the two pipelines is the key to diagnosis. If the answer is out of date, the problem is usually in the ingestion pipeline. If it is unrelated to the question, the problem is in the query pipeline.

Real-World Example

A research library. Ingestion: a clerk receives the new books, divides each book into chapters, writes an index card for each chapter (the title, the author, the year, and who is entitled to consult it), and sorts the cards. Query: a researcher comes with a question, the librarian searches the cards, picks the 5 most suitable chapters and hands them to the researcher to write the answer from them.

Key Terms

The chain of steps that prepares documents for search: extraction, cleaning, chunking, adding metadata, embedding and saving to the index.
Query pipelineخط الاستعلام
The steps carried out with every question: understanding it, searching, reranking, prompt assembly, generation and verification.
Chunkingالتقطيع
Splitting a document into small, searchable chunks (typically 200 to 800 tokens), with a small overlap between them so that no idea is cut off.
Upsertالإدراج أو التحديث
A single operation: if the item exists you update it, and if it does not you add it. Short for Update + Insert.
Stale chunksالمقاطع القديمة
Chunks from an old version of a document that remained in the index after it was updated, so they appear in search with information that is no longer correct.
Prompt assemblyتجميع الموجّه
Building the final text sent to the model: the instructions, the best chunks with their identifiers, and the question.
Citationالاستشهاد
Naming the source the information in the answer came from (document name, version and link), so that it can be verified.

What the Exam Tests

A RAG system consists of two separate pipelines: the ingestion pipeline, which runs offline or when the source changes, and the query pipeline, which runs live with every question. Understanding both together is the foundation for diagnosing any fault.

Ingestion pipeline (offline / on change)

  2. Parsing and cleaning → chunking, sized in tokens, with overlap.
  3. Metadata enrichment: doc_id, version, date, owner, classification and access control list (ACL).
  4. Embed → upsert into the vector index.
  5. Delete stale chunks.

Query pipeline (online)

  1. User → authentication → query rewrite.
  2. Query embedding.
  3. Retrieval: vector + keyword (hybrid) with metadata and permission filters.
  4. Rerank the top k → prompt assembly.
  5. LLM → answer with citations → guardrails → logging and tracing.

1.2 Keeping RAG Up to Date When Documents Change

In Plain Terms

This is one of the most frequently recurring scenarios in the exam: documents change, and the assistant gives out-of-date information. The table gives each symptom its cause and its fix.

The golden rule: the solution lies in the ingestion pipeline, the index and the cache, not in retraining the model. The freshness checklist has five items: (1) incremental indexing that processes only what changed, triggered by change events, (2) a version number and a “current” flag for every document, (3) deleting the old chunks, (4) cache invalidation for answers tied to the changed document, and (5) monitoring index freshness.

Real-World Example

The leave regulation was updated from “21 days” to “30 days”. The new version was added to the index, but the old one was not deleted. So the assistant sometimes finds the “21” chunk and sometimes the “30” chunk, and gives contradictory answers. Even after the old one is deleted, if the question “How much leave do I get?” is cached with the answer “21”, the assistant will keep giving that answer until the cache entry expires.

Key Terms
Incremental / delta indexingالفهرسة التزايدية
Updating the index with only the documents that changed, instead of rebuilding the whole index from scratch.
Change detection (CDC, webhooks, checksums)كشف التغيير
Ways to know that a document has changed: a notification from the source system (webhook), monitoring database changes (CDC), or comparing the hash.
Hash / checksumالبصمة
A short number computed from the content of a file. If a single character changes, the hash changes, so we know the file has changed without reading all of it.
Time-To-Live — TTLمدة الصلاحية
How long a cached copy stays valid before it is deleted and recomputed.
Cache invalidationإبطال التخزين المؤقت
Deleting cached answers because the information they were built on has changed.
Blue-green switchالتبديل الأزرق-الأخضر
Building a complete new version (an index or a system) alongside the old one, then switching all requests to it at once, with the ability to go back instantly.
Pre-filteringالتصفية المسبقة
Applying the permission conditions inside the search itself, so that documents the user is not entitled to see are never retrieved in the first place.

1.3 Diagnosing RAG by Stage

In Plain Terms

When a RAG system answers wrongly, identify the responsible stage first. Memorise three main cases: the correct document never appears in the results → the problem is in retrieval. It appears but at a low rank → the problem is in ranking. It appears at the top but the answer is wrong → the problem is in generation.

Two special cases: search misses exact terms (an article number, or a product code) → add keyword search (BM25). Answers about tables are poor → the problem is in how tables are read and chunked.

Real-World Example

You asked your assistant to bring the file “Al-Noor Company contract 2025”. (1) It did not find it in the archive at all: a search problem. (2) It found it but put it under 15 other files, so you did not see it: a ranking problem. (3) It brought it to the top of the pile, but summarised it wrongly for you: an understanding and writing problem. Each case has a different remedy, and fixing the wrong stage wastes effort.

Key Terms
Top-kأعلى k
The best k results from the search, such as the top 5 or 20 chunks.
Grounding instructionsالتأسيس على السياق
Instructions that tell the model to answer only from the given chunks, to cite them, and to say “I don't know” if it cannot find the answer.
Keyword / lexical searchBM25 / البحث بالكلمات
Search based on literal word matching. Strong on numbers, names and codes, where semantic search is weak.

1.4 Ingestion and Chunking Strategies

In Plain Terms

Search can find only what ingestion has prepared. Organisations' documents are a mixture: scanned PDFs, Word files, spreadsheets, presentations and emails, in Arabic and English. Good ingestion has six steps: extract the text with its structure → clean headers and repetition → normalise Arabic → chunk and add information → embed and index → record lineage.

There are many chunking methods, and the table compares them. The three most important are: document-aware (each article of a regulation is a chunk, and each question and answer is a chunk), parent–child (we search in small, precise chunks and send the model the larger section they belong to), and contextual chunks (we add the document name and section heading to each chunk, so that “Article 12” is not ambiguous as to which law it belongs to).

Real-World Example

A chunk reads: “An employee is granted 30 days of leave.” On its own we do not know: which law? which category of employees? which year? With contextual chunks it becomes: “[HR Regulation 2026 › Chapter 4: Leave › Article 12] An employee is granted 30 days of leave.” Now search can find it when an employee asks, “How much leave do I get under the 2026 regulation?”

Key Terms
Parserالمحلّل
A program that reads a file in a particular format (PDF, Word, HTML) and extracts its text and structure: headings, tables and lists.
Recursive chunkingالتقطيع التكراري
Splitting by headings first, then, if a section is large, by paragraphs, then by sentences, until every chunk is within the limit.
Semantic chunkingالتقطيع الدلالي
Splitting the text where the topic changes, by measuring the similarity between consecutive sentences.
Parent–child chunkingالأب والابن
Searching in small, precise chunks, then sending the larger section that contains them (the parent) to the model so that it gets sufficient context.
Contextual chunksالمقاطع السياقية
Prepending the document title or section summary to each chunk before embedding it, so that the chunk is understandable on its own.

What the Exam Tests

Retrieval can return only what ingestion has produced. Real enterprise repositories are a mixture of PDF files (some of them scanned), Word files, spreadsheets, presentations, HTML pages, emails and tickets — in Arabic, in English or in both.

A robust ingestion pipeline

  1. Extract the text together with its structure (headings, lists, tables, page numbers) using format-specific parsers, and Arabic-capable optical character recognition (OCR) for scanned files.
  2. Cleaning: remove headers, footers, repeated text and duplicate pages.
  3. Normalisation: Arabic orthography, whitespace and encodings.
  4. Chunking into passages, then enrichment with metadata.
  5. Embedding and indexing.
  6. Lineage recording: source, version, hash and ingestion time — so that any answer can be traced to its source and any document can be deleted.

1.5 Query, Retrieval and Reranking Techniques

In Plain Terms

Techniques for improving the search itself. Query rewriting: the follow-up question “And for contract employees?” is turned into the full question “How much annual leave do contract employees get?”. Multi-query: we generate several phrasings of the question and search with all of them. Decomposition: we split the complex question into sub-questions. Routing: we send the question to the appropriate source.

hybrid search: we search by meaning (vectors) and by words (BM25) together, then merge the two lists with a method called RRF. Its idea is simple: do not care about each system's scores, but about the document's rank in each list. A document that comes high in both lists moves up. Then reranking with a more precise model, which is often the single biggest improvement in quality.

Real-World Example

RRF calculated step by step. We use k = 60. Document (A) came first in the semantic search and third in the keyword search: 1 ÷ (60 + 1) + 1 ÷ (60 + 3) = 0.0164 + 0.0159 = 0.0323. Document (B) came second in the semantic search only: 1 ÷ (60 + 2) = 0.0161. So (A) moves ahead, because the two systems agreed on it.

Key Terms
Query rewritingإعادة صياغة الاستعلام
Turning the user's question (especially short follow-up questions) into a clear standalone question before searching.
Multi-hop questionsالأسئلة متعددة القفزات
Questions that require gathering information from more than one document in sequence, such as “Who is the director of the department that issued the leave regulation?”.
HyDE — Hypothetical Document Embeddingsالمستند الافتراضي
The model writes an imaginary answer to the question, then we search with that answer instead of the question, because its phrasing is closer to the phrasing of the documents.
Dense / sparse retrievalالبحث الكثيف والمتناثر
Dense: search by vectors (meaning). Sparse: search by words (BM25). They are combined in hybrid search.
Reciprocal Rank Fusion — RRFدمج الرتب التبادلي
A way of merging the results of several search systems by summing 1 ÷ (k + rank) for each document in each list. It needs no score calibration between the systems.
Maximal Marginal RelevanceMMR
A selection method that prefers chunks that are relevant and different from one another, so that we do not send five near-identical chunks.
Context compressionضغط السياق
Shrinking the retrieved chunks to the important sentences only before sending them, to save tokens and reduce distraction.

Hybrid search and reciprocal rank fusion (RRF)

Hybrid search runs dense vector retrieval and sparse BM25 keyword retrieval, then merges the results, often with reciprocal rank fusion (RRF). Its advantage is that it does not need score calibration across the two systems, because it relies on ranks, not scores.

RRF(d) = Σ 1 / (k + rank_i(d)) , k ≈ 60

Worked example: a document ranked 1 in the vector list and 3 in the BM25 list, and another document ranked 2 in the vector list only:

A: 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 = 0.03226
B: 1/(60+2) = 0.01613 → A ranks above B

Hybrid search is particularly valuable for Arabic: morphology and dialects weaken keyword-only search, while exact terms (article numbers, product codes, names) weaken semantic-only search.

Reranking, Diversity and Context Compression

  • Reranking with a cross-encoder (or an LLM) re-scores the top 20–100 candidates by reading the query and the chunk together, then keeps the best 3–8. It is often the single biggest quality gain after fixing chunking — at a cost of tens to a few hundred milliseconds.
  • Diversity (MMR — maximal marginal relevance) avoids sending five near-identical chunks.
  • Context compression shrinks the retrieved chunks to the important sentences, reducing tokens.

1.6 Beyond Basic RAG

In Plain Terms

Ordinary RAG searches texts and sends chunks. But some questions need something different. This table lists five advanced patterns, each with a signal in the question.

The two most important signals: an aggregate numerical question (“What is the total of claims in the last quarter?”) → do not search texts, but turn the question into a database query (SQL). A question about relationships across many documents (“Which suppliers are linked to delayed projects?”) → GraphRAG, that is, a network of entities and relationships.

Real-World Example

A question: “How many sick leaves were taken in the Finance department this year?” Text search will perhaps find documents about the sick-leave policy, but it will not count anything. Text-to-SQL, however, writes a query that counts the leaves in the database table and gives an exact number. It must be restricted: read-only, and specified tables only.

The model decides for itself when to search and what to search for, and repeats the search until it finds enough. Stronger for complex questions, and slower and more expensive.

Structured Query LanguageSQL

1.7 Evaluating RAG

In Plain Terms

RAG evaluation must separate two parts: the retriever (did it find the right chunks?) and the generator (did it write a correct answer from them?). Each part has its own metrics. For the retriever: context recall (did we find everything needed?) and context precision (is what we found relevant?). For the generator: faithfulness (is everything it said in the chunks?) and relevance (did it answer the question?).

A good test set contains real questions from users, in their dialects, follow-up questions, and questions with no answer in the documents, to test that the system says “I don't know” instead of inventing an answer.

Real-World Example

An assistant was asked, “How much is the end-of-service award for an employee who served 7 years?” Context recall: did it retrieve the award article? No → the problem is in search. Or it retrieved it, so we move on to the next: faithfulness: is the number in the answer the number in the article? No, it invented a number → the problem is in generation. Without this separation you will only know that “the answer is wrong”.

Did the system retrieve all the chunks needed for the correct answer?
Context precisionدقة السياق
How many of the retrieved chunks are really relevant, and are they ranked at the top?
Answer correctnessصحة الإجابة
Does the final answer match a known reference answer? An end-to-end metric.
Citation accuracyدقة الاستشهاد
Does the source the system cited actually contain the information attributed to it?
RAGAS frameworkRAGAS
An open framework that computes RAG evaluation metrics automatically using LLM judges.
Abstentionالامتناع
The system saying “I cannot find the answer in the documents” instead of inventing an answer.

Model-Serving Interfaces and Their Resilience

2.1 Choosing the Interaction Pattern for Serving Interfaces

In Plain Terms

How does the application communicate with the model? It depends on how long the task takes. Synchronous request (REST): the application asks and waits for the answer, and suits short tasks under a second or two. gRPC: like it but faster, for internal communication between services. Streaming (SSE or WebSocket): the answer arrives word by word, for chat. Asynchronous job: for long tasks (minutes), the application submits the request, is given a job number, and is then notified when it finishes.

The classic exam trap: a task that takes 5 minutes fails because the gateway cuts the connection after 60 seconds. The distractor option: “Raise the timeout to 10 minutes”. The correct answer: convert it to an asynchronous pattern with a queue.

Real-World Example

Synchronous: you order a coffee at the cashier and wait in front of them. Asynchronous: you hand your clothes to the laundry, they give you a numbered receipt, you go to work, and they call you when it is ready. If the laundry insisted that you wait at the counter for 3 hours, the solution is not “a bigger waiting chair”, but the receipt system.

2.2 Designing Model-Service Interfaces and HTTP Status Codes

In Plain Terms

When the server replies to a request, it attaches a three-digit status code that tells you what happened. Codes that start with 2 mean success, those that start with 4 mean that the error is yours (the requester's), and those that start with 5 mean that the error is the server's.

Four codes that people confuse, and the exam asks about them: 401 = “I don't know who you are” (you have not logged in). 403 = “I know you, but you are not allowed”. 400 = “Your request is written in a broken way”. 422 = “Your request is written correctly, but the values are not acceptable”.

Real-World Example

A government building. 401: the guard will not let you in because you did not show your ID. 403: you showed your ID and he recognised you, but this floor is for employees only. 400: you submitted a torn request form that cannot be read. 422: the form is written in clear handwriting, but you wrote your date of birth as 2090. 429: you submitted 100 requests in a minute, so you were told “Wait a little”. 503: the specialist employee is on a break, so come back shortly. 504: the employee went to search the archive and has taken far too long.

2.4 Authentication, Authorisation, Limits and Versions

In Plain Terms

Four security questions for every interface. Who are you? (authentication): users log in through OAuth and receive a temporary “ticket” (JWT), and services prove their identity to each other with certificates (mTLS). What are you allowed to do? (authorisation): decided inside the service, before searching the data, not after generating the answer. How many requests are you allowed? (rate limiting): in requests, and for LLMs in tokens as well. Which version? (versioning): /v1/ and /v2/, and the meaning of a field never changes.

Why authorise before the search? Because if the model sees a secret document it may mention something from it indirectly, and filtering the answer after it is written will not always catch that.

Real-World Example

A JWT is like a temporary entry pass for an event: sealed (it cannot be forged), with your name and the halls you may enter on it (the scopes), and it expires at 6 p.m. Every guard checks the seal and the date. The token bucket for rate limiting: a bucket that fills with one coin every second up to 10 coins. Each request takes a coin. If the bucket is empty, you wait. So you can send 10 requests at once, and then one request every second.

Key Terms

Authentication: verifying your identity (who are you?). Authorisation: determining what you are allowed to do (what can you do?).
OAuth / OIDCOAuth 2.0 / OpenID Connect
Standards for logging in and granting permissions, which let an application verify the user through a trusted identity provider.
JSON Web TokenJWT
A digitally signed access token that carries the user's identity, permissions and expiry date. It is verified on every request.
Mutual TLSmTLS
An encrypted connection in which both parties prove their identity with digital certificates, not just the server. For secure communication between services.
Role- / Attribute-Based Access ControlRBAC / ABAC
Ways of defining permissions: by role (manager or employee) or by attributes (department, classification, region).

A rate-limiting algorithm that allows short bursts within a defined average rate.
Deprecationالإيقاف
An announcement that an old version of the interface will stop working on a specific date, so that users can move before it.

What the Exam Tests

  • OAuth 2.0 / OpenID Connect for user-facing access, with short-lived JWT access tokens that carry scopes; verify the signature, expiry, audience and issuer on every request.
  • Service identities (workload identity, mTLS certificates) for service-to-service calls; avoid long-lived shared API keys.
  • Authorisation decisions inside the service (RBAC/ABAC), including data-level rules: which documents, tenants or records this caller may see — enforced before retrieval, not after generation.
  • Rate limiting with a token bucket or sliding window algorithm, per key/user/tenant; for LLMs there are also token quotas (input and output tokens per minute) and maximum request sizes, which protect cost and availability together (Unbounded Consumption in the OWASP list).
  • Versioning: in the path (/v1/) or in a header; never change the meaning of a field in place; publish deprecation schedules; and return the model version in every response for traceability.
Data permissions are enforced before retrieval; filtering the answer after generation is too late.

2.5 Resilience Patterns for LLM APIs

In Plain Terms

Systems break down, and the question is: how does your application withstand it? This table gives each problem a pattern. Four matter most. Retry with exponential backoff: if the request fails, wait a second and then retry, then two seconds, then four, with a small amount of randomness so that everyone does not retry at the same moment. The idempotency key: so that retrying does not create two requests. The circuit breaker: if the provider is completely down, stop contacting it temporarily and use an alternative. The timeout: never wait for any request forever.

The rule: retrying is safe only with an idempotency key, and retrying during a complete outage makes it worse, which is where the circuit breaker comes in.

Real-World Example

The circuit breaker is like the circuit breaker in your house. If a major fault occurs, the current is cut at once instead of the house burning. In software: after 5 consecutive failures from the provider, the application stops contacting it for 30 seconds and shows an alternative (a backup model or a polite message), then tries a single request, and if it succeeds it resumes work. bulkheads: like a ship's separate compartments; if one compartment floods, the rest do not.

Key Terms
Exponential backoff with jitterالتراجع الأسّي مع التذبذب
Doubling the waiting time between one attempt and the next (1, then 2, then 4, then 8 seconds) with a small amount of randomness added, so that clients' attempts do not coincide.
Circuit breakerقاطع الدائرة
A pattern that stops requests to a failing service temporarily after consecutive failures, uses an alternative, and then tests whether it has recovered.
Bulkheadsحواجز العزل
Separating the resources of each dependency (such as the number of threads), so that one slow service does not consume all the application's resources.
Secrets manager / Vaultالخزنة / مدير الأسرار
A secure system for storing passwords and API keys, which gives them to the application only when needed and supports rotating them.
Web Application Firewall — WAFجدار حماية تطبيقات الويب
A protection layer in front of interfaces that blocks known malicious requests.
Virtual Private Cloud — VPCشبكة خاصة افتراضية
An isolated network inside the cloud, which cannot be reached from the public internet except through specified ports.
Tenant isolationعزل المستأجرين
Guaranteeing that the data of each customer in a shared system is never seen by another customer.

2.6 Structured Outputs and Validation

In Plain Terms

When another program (not a human) reads the model's outputs, they must be in a fixed format it can understand. The method has four steps: define the required shape precisely (a JSON schema) → use the provider's “structured outputs” feature → validate the output → if validation fails, retry with the error message, or use a fallback.

The security rule: treat model outputs as untrusted input. Do not execute them as commands, and do not put them directly into a database query or a web page without cleaning. Because whoever controls the model's inputs may control its outputs.

Real-World Example

You ask the model to extract invoice data in the form: {“amount”: number, “date”: date, “supplier”: text}. It replies once with {“amount”: “five hundred riyals”}. Text instead of a number, so validation fails, and we resend the request with the message “The amount must be a number”. A security example: if we put the supplier name that the model extracted directly into a database query, and the name written on the invoice was malicious text, it could delete a whole table.

Key Terms
JSON Schemaمخطط JSON
A formal description of the shape of a JSON object: the fields, their types, and which of them are mandatory. Used for automatic validation.
Constrained decodingالتوليد المقيَّد
Forcing the model, during generation, to produce only tokens that conform to a specified format, so that the output always has the correct shape.
PydanticPydantic
A common Python library for verifying that data matches a specified shape.
Sanitisationالتعقيم
Cleaning data of any content that might be interpreted as commands before it is used in a query, a page or a system command.
Improper output handlingالمعالجة غير الآمنة للمخرجات
One of the OWASP risks for LLMs: using the model's outputs directly in other systems without validation, so that they become a vulnerability.

What the Exam Tests

When model outputs feed other software, follow this sequence:

  1. Define a JSON schema.
  2. Use the provider's structured-output feature, function calling or constrained decoding.
  3. Validate the output (for example with Pydantic).
  4. On failure, retry with the validation error message, or use a fallback.
Treat model output as untrusted input: do not execute it, and do not pass it to SQL, commands or HTML without sanitisation (Improper Output Handling in OWASP).

2.7 Caching

In Plain Terms

Caching saves previous results to return them quickly without running the model. Its types: exact match (the very same question word for word), semantic (a question similar in meaning), prefix caching (the static part of the prompt), and the embedding cache (we do not re-embed a chunk that has not changed).

Three rules the exam asks about: (1) Invalidate it when the document changes. (2) Do not share it between users with different permissions. (3) Put the static part of the prompt first so that prefix caching works.

Real-World Example

The semantic cache and its risk: an employee asked, “What is the project manager's salary?” and had permission, so the answer was cached. Then another employee without permission asked, “What is our project manager's pay?” The question is semantically similar, so the cache returned the saved answer. Now the employee has seen information he is not entitled to see. That is why the cache is not shared across different permissions.

The existence of a saved answer for the request, so it is returned immediately without computation. Its opposite is a miss.
Semantic cacheالمخزن الدلالي
A cache that returns a saved answer for a question similar in meaning (vector similarity above a threshold), not an exact literal match.
vLLMvLLM
A popular open-source program for running LLMs efficiently on GPU servers.

3.1 Integration Architecture Patterns

In Plain Terms

How do systems connect to each other? This table lists eight patterns. The simplest is request–response: I ask and wait. Then the queue with workers: I put the job in a queue and a worker takes it when free. Then events: I announce “such-and-such happened”, and whoever is interested acts. Then CDC: every change in the database is broadcast as an event. Then Saga: a transaction of several steps, where each step has an “undo” in case what follows it fails.

A recurring question: do I put the model inside the application itself or in a separate service? Inside is simpler if one team owns both. Separate if the model needs a GPU, or scales differently, or is released at a different cadence, or is used by several applications.

Real-World Example

Saga, with the example of booking a trip: (1) book the flight, (2) book the hotel, (3) book the car. If the car fails, we do not leave the flight and hotel booked to no purpose. Each step has a “compensation”: cancel the hotel, then cancel the flight. That is why the compensation is designed in advance for each step. This matters with agents that carry out real transactions.

Workerالعامل
A program that takes jobs from the queue and executes them one after another. More workers can be run as jobs increase.
Publish–subscribe (pub-sub)النشر والاشتراك
A pattern in which the producer publishes messages to a “topic”, and all subscribers to that topic receive them.
Schema evolutionتطور المخطط
The shape of the data changing over time (adding a column or changing its type) while keeping the systems that depend on it working.
Saga / compensating actionsSaga والإجراءات التعويضية
A chain of steps, each with a compensating action that undoes its effect if a later step fails.
Service meshشبكة الخدمات
An infrastructure layer that manages the communication between services (encryption, retries, measurement) without changing their code, through a helper container beside each service.
Strangler patternنمط الإحلال التدريجي
Replacing an old system gradually by adding the new one beside it and moving an increasing share of requests to it.
Microservicesالخدمات المصغّرة
Dividing the application into small independent services, each with a single responsibility, that communicate through interfaces.

3.2 The LLM Gateway Pattern

In Plain Terms

When several teams in an organisation use LLMs, each team calls the provider with its own keys: nobody knows the total spend, or what data is being sent, and each team rebuilds the same thing. The solution is the LLM gateway: a single central point through which all requests pass.

The gateway takes on eight responsibilities: who may do what (and the budget), which model for each request, data protection (restricted data leaves only to approved models inside the Kingdom), resilience, caching, monitoring and cost, guardrails, and audit. An important warning: the backup alternative when a provider fails must also respect the data classification.

Real-World Example

A company with 10 departments, and each department orders taxis on its own account. At the end of the month nobody knows how much was spent, or where the employees went. The solution: a single central transport office: it orders the cars for everyone, applies a policy (no trips outside the city without approval), chooses the cheapest option for short trips, and gives each department a report of its spending.

Key Terms
LLM gatewayبوابة النماذج اللغوية
A central layer between the organisation's applications and the model providers, which handles authentication, quotas, routing, data protection, resilience, caching, monitoring, guardrails and audit.
Data Loss Prevention — DLPمنع فقدان البيانات
Controls that detect sensitive data (ID numbers, health data) and mask it or prevent it from leaving the organisation.
Failoverالتحويل الاحتياطي
Automatic switching to an alternative provider or version when the primary one fails.

What the Exam Tests

Organisations with several LLM-dependent applications typically place an LLM gateway between the applications and the model providers (external APIs and self-hosted models). The gateway concentrates responsibilities that every application should not have to rebuild:

  1. Authentication and per-team quotas — who may call which model, with token budgets.
  2. Routing — choosing a model per request (by task, cost tier, data classification or language); and a cascade from a small model to a large one when confidence is low.
  3. Data protection — classifying requests, and masking or blocking personal and classified data before it leaves the boundary (data loss prevention, DLP), and enforcing the rule “restricted data goes only to approved models inside the Kingdom”.
  4. Resilience — retry with backoff, timeouts, circuit breakers and failover between providers.
  5. Caching — exact-match and semantic response caches, and prefix caching where supported.
  6. Observability and cost — logs of the model, version, tokens, latency and cost per team; and tracing for debugging.
  7. Guardrails — input filters (injection patterns, policy violations) and output filters (personal data, toxicity, schema).
  8. Audit — retained according to the retention policy with personal data minimised.
In the scenario “each team calls the external models directly with its own keys, and nobody knows the spend or the data sent” → the LLM gateway is the expected architectural answer.

Note: failover in the gateway must respect data classification; the fallback during a provider outage must not be a non-approved model for restricted data.

In Plain Terms

In Plain Terms

4.2 Testing AI-Powered Software

In Plain Terms

Testing is layers, each testing something: unit, contract, data, model quality, behaviour, safety, full integration, performance and fairness. What is new with LLMs is behavioural testing: does changing the phrasing of the question change the classification? It should not. Does it work with different dialects?

The biggest challenge is non-determinism: the model may answer with different wording each time. So do not test the literal text, but the properties: is the output valid JSON? Does it have the required fields? Did it cite a source? Did it refuse the forbidden request? Run the important case several times and measure the pass rate.

Real-World Example

A bad test: “The answer must literally equal: Annual leave is 30 days”. It will fail if the model writes “The annual leave period is thirty days”, even though that is correct. A good test: “The answer contains the number 30 or thirty, cites Article 12, and does not exceed 100 words”. We run it 10 times: if it passes 10 out of 10, excellent, and if it passes 7 there is instability that must be understood.

4.3 Observability for AI Systems

In Plain Terms

Observability is being able to know what is going on inside your system. It has three pillars: metrics (aggregated numbers: latency, error rate, cost), logs (discrete events: “Request such-and-such was rejected for such-and-such a reason”), and tracing (the journey of a single request through all the steps).

In LLM applications the trace must show every step: the guardrail check, rewriting the question, the search (and which documents it found and with what score), reranking, the model call (which model, which version, how many tokens, how many seconds), and the tools. Even so, respect privacy in the logs: mask personal data, restrict who sees the logs, and delete them after a period.

Real-World Example

A user complains: “The assistant is very slow”. The metrics tell you: p95 rose from 2 to 8 seconds today. The trace of a slow request shows: guardrails 50 ms, search 100 ms, reranking 6 seconds, the model 1 second. Now you know exactly where the problem is: the reranking model. Without tracing you would have been guessing.

4.4 Conversational AI Design

In Plain Terms

A good conversational assistant is not “an LLM behind a chat box”. It is a system that understands what the user wants and decides the appropriate route. Intent routing first: the question “What is my balance?” is answered from the system directly without an LLM (faster, cheaper and more accurate). A question about policies goes to RAG. A request “Change my plan” goes to a transaction path. Sensitive matters go to a human.

For transactions: collect the required slots (account, date, amount), validate them, confirm with the user, then execute with an idempotency key. Do not let the model carry out a transaction from free text. handover to a human has triggers: the user's request, low confidence, repeated failure, a sensitive subject, or a high value. Pass on the conversation summary so that the user does not repeat themselves.

Real-World Example

A user writes: “I want to cancel the internet plan.” The assistant: “Which number?” → “0501234567”. The assistant verifies that the number belongs to the user and has an internet plan on it. Then it says: “You want to cancel the monthly internet plan on number 0501234567 effective 1 Muharram. Do you confirm?” → “Yes”. Then it executes. This is slot filling and then confirmation. If the user wrote, “I'm very upset and this is the third time I've called”, that is a sign of distress that calls for handover to an agent.

4.5 Engineering Reliable Agents

In Plain Terms

You saw the controls for agents in Unit 05. Here are the engineering practices for making them reliable. The most important: an explicit workflow (a state machine) instead of a free loop, typed tools that catch the wrong call before it is executed, reversible tools, read/write separation, budgets for steps, time and cost, checkpoints for resuming after failure, and full tracing.

Agents fail in ways different from ordinary programs: they misunderstand the goal, call the wrong tool, go round in loops, or stop early. The most important rule: known sequence → fixed workflow with LLM steps, not an open-ended agent.

Real-World Example

The state machine for a refund request: [receive the request] → [check eligibility] → [calculate the amount] → [wait for approval] → [execute] → [notify]. The model fills in specific steps (extracts the reason for the refund, writes the notification message), but it does not decide the order of the steps and does not jump from “receive” to “execute”. If the system fails at “wait for approval”, it resumes from there, not from the beginning.

A design that defines the possible states (such as: new, pending, approved, executed) and only the allowed transitions between them.

Tools with a precise schema for their parameters (a number, a date, or a value from a list), so that any call that does not match it is rejected before execution.
Idempotentمتساوي الأثر
An operation where executing it twice gives the same result as executing it once, so retrying is safe.
Checkpointنقطة الحفظ
Saving the state of the task at a particular moment, so that it can be resumed from it after a failure instead of starting again.

Handling failure

Agents fail differently from interfaces: they misunderstand goals, call the wrong tool, go round in loops, or stop early. Design for that: detect repeated identical calls, set a retry ceiling per tool, fall back to asking the user or a human, and summarise partial progress.

Plan → confirm the plan with the user (for tasks with side effects) → execute with checkpoints → deliver the report

When not to use an agent

If the task follows a known sequence, a deterministic workflow with LLM steps is cheaper, faster and more reliable. Resort to open-ended agents only when the path genuinely cannot be determined in advance — and then with their permissions restricted.

Applied Scenario

Apply the stage-by-stage diagnostic method and the resilience and integration patterns to an enterprise RAG assistant over documents that change periodically.

The Scenario

A government entity in Riyadh launched an internal assistant that answers employees' questions about regulations and administrative policies, built on RAG over about 40,000 documents (PDFs, some of them scanned, Word files and FAQs). The index is rebuilt in full every night, and the assistant is served through a synchronous HTTP call from the API gateway.

Two months later the following complaints appeared: after the leave regulation was updated, the assistant went on citing the old version for hours, and sometimes even showed both versions with contradictory answers; questions such as “What is the text of Article 17?” were returned with other articles; and an employee in a general department saw a passage from a confidential HR memo.

At the same time, management asked for a “summarise the whole case file for me” feature that takes 3–5 minutes, so requests began failing with gateway timeouts and being retried automatically, and the external provider's bill rose. It was also discovered that two other teams are calling the same provider directly with their own keys.

Solution Steps

  1. Classify each complaint by its stage: citing the old version → ingestion/index (and possibly the cache); both versions together → no current-version flag; Article 17 → semantic-only retrieval; the confidential memo → permissions not enforced at retrieval; summarisation failure → wrong interaction pattern.
  2. Replace the nightly rebuild with incremental indexing triggered by change detection (document-management-system events or hashes), with an upsert by doc_id and deletion of the superseded chunks, and publish a freshness agreement such as “indexed within 15 minutes”.
  3. Add version, effective_from and is_current metadata and filter to the current version by default, and invalidate the cache entries tied to the changed documents.
  4. Add BM25 in a hybrid search merged with RRF, chunk the regulations one article per chunk with the name of the law prepended to each chunk (contextual chunks), and add a reranker.
  5. Enforce the access control list inside the retrieval query (pre-filter) based on the user's groups from the identity system, not by filtering the answer after generation.
  6. Turn the summarisation feature into an asynchronous pattern: 202 Accepted with a job_id, a queue and workers, and a notification via a signed webhook or polling, with idempotency keys and retry with exponential backoff and jitter.
  7. Place a shared LLM gateway across the three teams: authentication and token quotas per team, masking of personal and classified data, routing by data classification, cost logging per team, and caching.
  8. Prove the improvement with a golden set that measures context recall and precision separately from faithfulness and answer correctness, and make it a gate in CI on every change to the prompt or model.

Exam Traps

  • “Fine-tune the model on the new regulations” — freshness is an index and ingestion problem, not a weights problem.
  • “Raise the gateway timeout to 10 minutes” — long jobs need a queue-based asynchronous pattern.
  • “Filter the answer after it is generated to hide the confidential content” — permissions are enforced before retrieval.
  • “Rebuild the index every hour instead of every night” — it remains slow and expensive; the correct fix is incremental indexing with hashes and change events.
  • “Change the embedding model and re-embed only the new documents” — this mixes the vectors of two models; re-embed the whole corpus into a new index and do a blue-green swap.
  • “A semantic cache shared by all employees saves cost” — it must not be shared across users with different permissions.

  1. 1An entity updated its regulation, and the assistant still cites the old version even though the indexing log confirms that the new version was inserted. What is the most likely cause, and what is the fix?
    Answer

    Either the old chunks were not deleted, or a response cache is serving stale answers. The fix: delete the superseded chunks on upsert by doc_id, an is_current flag with filtering on it, and invalidation of the cache entries tied to the changed document.

  2. 2The correct document appears at rank 15 in the retrieval results. Which stage do you fix, and how?
    Answer

    The ranking stage: add a cross-encoder reranker over the top 20–100 candidates and keep the best 3–8, and tune k. The document is already retrieved, so changing the embedding model is not the first fix.

  3. 3Calculate the RRF score for a document ranked 2 in the vector search and 1 in BM25, with k = 60.
    Answer

    1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 ≈ 0.0325. The advantage of RRF is that it merges by rank, so it does not need score calibration between the two systems.

  4. 4What is the difference between status codes 401 and 403, and between 400 and 422, in a model service?
    Answer

    401 means the caller is not authenticated (missing or expired token), and 403 means authenticated but without permission for the model or data. 400 is a malformed input (invalid JSON), and 422 is well-formed syntax with semantically invalid values or a schema-validation failure.

  5. 5A POST request to create a ticket was retried after a timeout and created two tickets. Which pattern is missing? Which code is appropriate if the same key is reused with a different payload?
    Answer

    Idempotency keys make retrying safe. Reusing the same key with a different payload returns 409 Conflict.

  6. 6When is the LLM gateway the expected architectural answer?
    Answer

    When several teams call the external models directly with their own keys and nobody knows the spend or the data sent. The gateway concentrates authentication, quotas, routing, data protection, resilience, caching, observability, guardrails and audit.

  7. 7Why is a shared semantic cache not enough in a multi-department internal assistant?
    Answer

    Because it may return an answer to a subtly different question, and because it must not be shared between users with different permissions, as it could reveal restricted content to someone not entitled to see it.

  8. 8How do you test a feature that depends on an LLM whose outputs are non-deterministic?

  9. 9You are asked to build an agent that handles refund requests that always follow the same steps. What is the most suitable design?
    Answer

    A deterministic workflow with LLM steps, because it is cheaper, faster and more reliable than an open-ended agent. Open-ended agents only when the path cannot be determined in advance, and with restricted permissions and human approvals for irreversible actions.

  10. 10When do you separate the model into an independent service instead of serving it inside the application process?
    Answer

    When the model needs a GPU, independent scaling or its own release cadence, or is shared by several applications; the usual scenario signal: the web tier and the model need very different hardware and scaling.

The memo's guidance is that prefix caching only helps if the prefix is identical — keep the static part first. Moving the variable fields after the 3,000-token block makes that block a shared prefix for every request. A longer TTL cannot help when no two prefixes match; trimming instructions sacrifices content and still caches nothing; a semantic cache is a different tool with staleness and wrong-answer risks.

  7. 7Evaluation gates in CI for prompt changesHard

    A telecom operator's chatbot team merges prompt changes after a developer manually checks about ten sample questions. A recent change improved English answers but quietly degraded answers to questions written in Gulf dialect; customers reported it two weeks later, after satisfaction scores had dropped. The team ships prompt updates several times a week and does not want to slow releases down significantly. Which practice best prevents a repeat?

    Explanation

    The memo's practice is 'eval tests in CI': a golden set run automatically on every prompt or model change, with merges blocked when it regresses. A representative set covering dialect phrasing, follow-ups and unanswerable questions would have caught the dialect drop before release, and an automated run adds minutes rather than days, so frequent releases continue. A bigger manual sample is slower and still unsystematic; production satisfaction scores detect the problem only after customers are hurt; fine-tuning is the retrain reflex and does not stop future prompt changes from causing regressions.

  8. 8Chunking regulations and FAQsHard

    A municipality is building a RAG assistant over 300 building regulations, each organised as numbered articles (some containing tables of setbacks), plus a 1,500-entry FAQ. Inspectors ask precise questions such as 'What does Article 27 require for corner plots?'. A prototype using fixed 400-token chunks with 15% overlap often retrieves half an article, or an FAQ answer separated from its question. The team has one sprint to fix retrieval quality before a pilot. Which chunking approach is most appropriate?

    Explanation

    Retrieval can only return what ingestion produced. For regulations and FAQs, the memo's highest-precision strategy is document-aware chunking: each legal article becomes a chunk with its title prepended, each FAQ question stays with its answer, and tables are kept intact with their headers. This matches how inspectors ask ('Article 27') and fits in one sprint because the structure is regular. Bigger fixed chunks still cut articles at arbitrary points and dilute precision; semantic chunking ignores article boundaries and needs tuning; a reranker cannot reassemble chunks that ingestion broke apart.

  9. 9Mapping status codes for safe retriesHard

    A document-classification API returns 500 Internal Server Error for every failure: quota exceeded, invalid input, model warming up after a deployment, and genuine bugs — sometimes with a stack trace in the body. Client SDKs retry every 500, so malformed requests are retried endlessly and quota breaches turn into retry storms. Which change best fixes the API's contract?

    Explanation

    Status codes tell clients what to do next. The memo's mapping: 400 for malformed input and 422 for semantically invalid input — not retryable; 429 when a quota is exceeded, including Retry-After so clients back off for the right time; 503 when the model is warming up or capacity is exhausted — retryable; 500 for unexpected bugs, never leaking stack traces. With correct codes, SDKs retry only what can succeed. Returning 200 for errors breaks HTTP semantics and monitoring; blanket 503 invites retries of bad input; documentation cannot change what generic retry logic does with a 500.

  10. 10In-process model vs. separate model serviceHard

    A retailer's web storefront runs on CPU nodes that autoscale sharply during sales. A new recommendation model needs GPUs, is retrained and released weekly by a separate data-science team, and will also be called by the mobile app and the call-centre application. Recommendations must reflect clicks made in the current session. The web team proposes loading the model inside the storefront process to avoid a network hop. Which deployment is most appropriate?

    Explanation

    In-process serving is simplest and fastest only when one team owns both the application and the model and their hardware and scaling match. Here every cue points the other way: the web tier needs CPU and sharp autoscaling while the model needs GPUs; the model has its own weekly release cadence and owner; and three applications share it. The memo's rule is that this calls for a separate model service with a stable, versioned interface. A nightly batch fails the current-session requirement, and per-app copies multiply GPU demand and create version drift. Lesson: very different hardware and scaling → separate service.
