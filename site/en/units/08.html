Unit Introduction

This domain covers about 19 of the 150 items and overlaps heavily with the cost questions. The terms that recur in the questions are familiar: latency in milliseconds, replicas, cost, and hours of high load. The idea the exam tests is a single one: right-sized architecture — enough to meet the service-level objective (SLO) at peak, and no more. This unit builds the tools you need for it: choosing the right inference mode, understanding the hardware that sets speed, calculating weight memory, KV-cache memory and replica counts, then tuning latency, caching and cost, together with the in-Kingdom residency constraints that turn hosting location into an architectural requirement.

Before You Start

This unit is about where and how the system runs: do we run the model online or overnight? On which machine? How many machines do we need? Where in the Kingdom do we host it? How do we make it fast and cut its bill? It is Domain 5 (about 19 questions out of 150), and it holds the calculations that recur most often in the exam: memory and the number of machines.

You do not need to be a network engineer. You will need three skills: to ask “is anyone waiting for the answer?”, to work out “how much memory and how many machines?” by multiplying and dividing, and to look for “where do the time and the money actually go?”.

Before this, you need: Unit 00 (Section 2.6 and the whole of Chapter 5), Unit 01 (Sections 3.5 and 4.5), and Unit 04 (Sections 2.4 and 2.7: KV-cache memory and generation speed).

Learning Outcomes

By the end of this unit, you will be able to:

  • Choose the right inference mode (online, batch, streaming, edge, pre-computation) from the latency need and the input pattern.
  • Calculate weight memory, KV-cache memory and concurrent sequences per GPU, then the GPU count needed for peak with an N+1 margin.
  • Distinguish memory-bandwidth-bound stages from compute-bound ones, and choose the GPU using the logic: memory → latency → throughput → lowest cost per useful unit.
  • Design a sound scaling policy on Kubernetes (scaling metric, minimum replicas, scheduled scaling, load shedding) and handle cold starts.
  • Diagnose the source of latency from traces and choose the right remedy for each source, while designing caching layers whose keys are safe.
  • Choose the hosting and pricing model (managed, self-hosted, in-Kingdom, Spot, reserved) according to volume, sensitivity, classification and unit economics.
  • Match a scenario to one of the three reference architectures and check each component against the requirements.

How to Study This Unit

Study the unit through the numbers, not the names. Every decision table in it answers one question: what is the minimum infrastructure that meets the requirement? Recalculate the GPU example (8 GB, 2 TB/s, 250 tokens/s) and the full capacity-planning example step by step, until you can change one number (prompt length, number of users) and trace its effect on the GPU count. Then memorise “the patterns behind the correct answers”: nobody is waiting → batch; slow after a quiet period → cold start, not a bigger GPU; saturated GPU with low CPU → scale on the queue, not on CPU; a cache shared across different permissions → a leakage vulnerability. In every scenario ask: where does the data sit? How does it scale? What happens on failure? What does a useful unit cost?

Chapter 1

Deployment Patterns, Hosting and Reference Architectures

1.1 Online, batch, streaming or edge

In Plain Terms

The first decision: when does the model run? There are five modes. Online: the user is waiting now (a fraud score at the moment of payment, or a chat). Batch: once a day for all the data (scores for every customer overnight). Streaming: it follows the data as it arrives, within seconds or minutes. Edge: on the device itself, with no internet. Pre-computation then lookup: we compute all the results in advance and read them from a table on request.

The two questions that settle the decision: is anyone waiting for the answer right now? and are the inputs known in advance? If nobody is waiting, there is no sense paying for machines that run all the time.

Real-World Example

A bank wants a “probability of leaving” score for each of 10 million customers, for the sales staff to see in the morning. The distractor: “an online endpoint running 24 hours with autoscaling”. The correct answer: a nightly job on cheap machines that computes the 10 million scores and writes them to a table, and in the morning the system reads the score from the table in a fraction of a second. The cost is a small fraction of the online option, and the result is the same.

Key Terms
Online / real-time inferenceالاستدلال الفوري
Running the model at the moment the request arrives, with the user waiting for the result for fractions of a second or a few seconds.
Batch inferenceالاستدلال الدفعي
Running the model once, at a set time, on a large amount of data, with nobody waiting.
Streaming inferenceالاستدلال التدفقي
Running the model on events as they flow continuously, with a delay of seconds to minutes.
Pre-computationالحساب المسبق
Computing the results before anyone asks for them and saving them, then reading them instantly when needed.
Microsecond (µs)الميكروثانية
One millionth of a second, that is, one thousandth of a millisecond.

What the Exam Tests

The common distractor here is proposing an online endpoint with autoscaling for a task that is refreshed once a day. The correct answer is cheaper and simpler: a nightly job on Spot instances that writes the results to a table that is read by lookup.

1.2 Scaling patterns

In Plain Terms

How do we carry a bigger load? Horizontally, with more replicas behind a request distributor, or vertically, with a bigger machine that has a ceiling. Autoscaling adds replicas when the load rises. Scheduled scaling adds them before known peaks. Scale-to-zero keeps no replica when unused, but the first request after it is slow.

An important point about load balancing: the “round-robin” method (one request per replica in turn) is bad for language models, because one request takes half a second and another twenty seconds. Better is “send to the replica that is least busy right now”. The availability rule: at least two replicas in two different zones.

Real-World Example

A restaurant with 3 cashiers. With the “round-robin” method: the first customer goes to cashier 1, the second to 2, the third to 3, then the fourth to 1… But the first customer ordered for a family of 15 people and takes 10 minutes, so cashier 1’s queue piles up while 2 and 3 are empty. The smarter way: “go to the shortest queue”. That is “least outstanding requests”.

A component that receives all the requests and distributes them across the service’s replicas.
Kubernetes autoscalersHPA / KEDA
Tools in Kubernetes that add or remove replicas automatically: HPA by metrics such as CPU or custom metrics, and KEDA by events such as queue length, and it supports scale-to-zero.
Scale-to-zeroالتقليص إلى الصفر
Stopping all replicas when there are no requests, so you pay nothing, in exchange for a slow first request afterwards.
Round-robinالتناوب الدائري
Distributing requests across the replicas in turn, without looking at how busy each one is.
Least outstanding requestsأقل الطلبات المعلقة
Sending the new request to the replica that has the fewest requests currently in progress.
Queue-based load levellingتسوية الحمل بالطابور
Putting requests in a queue that absorbs sudden bursts, so the replicas process them at a steady pace.
Shardingالتجزئة
Dividing the data or the index into parts on different machines, each machine responsible for one part.

1.3 Cold starts

In Plain Terms

Cold start: a new replica of a large model needs minutes before it can answer. It downloads the weights file (gigabytes), then loads it into GPU memory, then warms up. So if the service is “scaled to zero”, the first user in the morning waits minutes or times out.

The fix is not “a stronger machine” (it does not speed up download and loading), nor “a longer timeout” (it only hides the problem). The fix: at least one replica always running, pre-warming before the peak, and faster loading (keeping the model on the machine itself, or a smaller quantised file).

Real-World Example

A car in bitter winter: after a cold night it needs minutes to warm up before it moves comfortably. If you were an ambulance driver, you would not switch the car off completely between shifts. Buying a bigger engine will not make it warm up faster. The fix is to keep it warm, or to start it ten minutes before the departure time.

Key Terms
Cold startالبداية الباردة
The delay when starting a new replica from zero: downloading the model, loading it and warming it up, which can reach minutes with large models.
Warm-upالتسخين
Sending trial requests to a new replica to prepare its memory and libraries before it receives user requests.
Minimum replicasالحد الأدنى للنسخ
The number of replicas that autoscaling never goes below, even in the quietest periods.

What the Exam Tests

A cold start for large models can take minutes: downloading the weights, then loading them into GPU memory, then warm-up. Scale-to-zero therefore saves cost but pays for it on the first requests.

If a scenario complains that “the first requests after a quiet period are very slow or time out”, the fix is: minimum replicas ≥ 1, pre-warming before scheduled peaks, and faster model loading (local cache, smaller or quantised artefacts) — not “a bigger GPU”.

A bigger GPU does not shorten download and load time, and lengthening the timeout hides the problem from the user instead of solving it. These are the two usual distractors.

1.4 Cloud, hosting and pricing

In Plain Terms

Where do we run the system? There are many options, each with an advantage and a price. Managed model API: the fastest start with no machines, but the data leaves your boundary. Managed platform: ready-made tools at an extra cost. Self-hosting: full control and cheaper at high, steady volume, and it needs a skilled team. In-Kingdom cloud regions: for regulated data. Serverless: you pay only when you use it, with cold starts.

The pricing options: Spot is 60–90% cheaper but can be reclaimed suddenly, so it suits only training and batches. Reserved is 30–60% cheaper with a commitment of a year or more, so it suits the permanent minimum. The rule: small or uncertain volume → a managed service. High, steady volume, sensitive data and a capable team → self-hosting inside the Kingdom.

Real-World Example

Commuting to work every day. A taxi app (a managed API): you own no car and no maintenance, you pay per trip, and it is excellent if you travel little. Buying a car (self-hosting): investment, maintenance and insurance, but if you drive 100 kilometres a day it is far cheaper in the long run. The break-even point: the number of trips at which the two costs are equal.

Key Terms
Managed serviceالخدمة المُدارة
A service that the provider runs on your behalf (the machines, the updates, the scaling), and you pay for use.
Sovereign cloudالسحابة السيادية
Cloud infrastructure inside the country’s borders and under its regulations, for hosting government and regulated data.
Reserved / committed useالمحجوز / الاستخدام الملتزم
A commitment to use a certain capacity for one or three years in return for a large discount; you pay even if you do not use it.
Preemptibleالقابل للاسترداد
Another name for Spot capacity: very cheap, and the provider can take it back at short notice.
Break-even pointنقطة التعادل
The volume at which the costs of two options are equal, such as paying per token versus self-hosting.

1.5 Sovereign and in-Kingdom architecture

In Plain Terms

In Saudi Arabia, the hosting location is not a technical detail but a legal requirement, because of data classification and the Personal Data Protection Law (PDPL). Four patterns: (1) Everything inside the Kingdom: the model, the index, the logs, the backups and the recovery site. (2) Classification-based routing: public data may go to an approved external service, and everything else stays inside the Kingdom. (3) Hybrid with redaction: personal data is removed before anything is sent outside. (4) Bring the model to the data instead of the reverse.

Two warnings that recur in the exam. The backups and the recovery site are part of the requirement, not the model alone. pseudonymised data is still personal data. SDAIA’s generative-AI principles for government entities: a government employee uses generative tools only with public data.

Real-World Example

A government entity said “our whole system is inside the Kingdom”. The auditor’s check: the model is inside the Kingdom ✓, and the vector database is inside the Kingdom ✓, but the nightly backups are sent to a data centre in another country “because it is cheaper”, and the logs (which contain citizens’ questions) are analysed by an external service. So the system is not actually “entirely inside the Kingdom”. The five questions in the checklist reveal this.

Key Terms
Data residencyإقامة البيانات
A requirement that data be stored and processed inside specified geographical borders, such as the Kingdom.
Data classificationتصنيف البيانات
Dividing data by its sensitivity (public, restricted, secret, top secret) to determine its protection controls and where it is hosted. You will see it in Unit 10.
Open-weight modelsالنماذج مفتوحة الأوزان
Models whose weights are published, so they can be downloaded and run inside your environment without sending data to any provider.
National Cybersecurity Authority — NCAالهيئة الوطنية للأمن السيبراني
The Saudi authority responsible for cybersecurity; it issues controls, including the cybersecurity controls for cloud computing.

What the Exam Tests

Data classification and the PDPL transfer rules turn hosting location from an operational detail into an architectural requirement. There are four common patterns:

  1. Fully in-Kingdom: models, vector stores, logs, backups and disaster-recovery sites are all in approved regions or data centres inside the Kingdom. Required for the higher classifications, and typical for government personal data. Note: backups and the recovery site are part of the requirement, not the model alone.
  2. Classification-based routing: an LLM gateway sends “Public” data to approved external services if that is permitted, and everything else to models inside the Kingdom. Under SDAIA’s generative-AI principles for government entities, government staff use generative tools only with Public data.
  3. Hybrid with redaction: personal data is removed or replaced with pseudonyms before any external call — remembering that pseudonymised data remains personal data, and that redaction is never complete.
  4. Bring the model to the data: deploy open-weight models inside the data owner’s environment instead of moving the data to the model.

Checklist questions

  • Where are prompts, outputs, embeddings and logs stored?
  • Where are the backups and the disaster-recovery copies?
  • Who can access them, including the provider’s support staff?
  • What does the contract say about using the data for training?
  • Is the cloud provider approved for the classification level (the cloud cybersecurity controls issued by the National Cybersecurity Authority (NCA))?

1.6 Edge and on-device AI

In Plain Terms

Edge AI means running the model on the device itself (a phone, a camera, or a machine in a factory) instead of sending it to the cloud. Four reasons for this: speed (no trip across the network), working offline, privacy (the data does not leave the device), and saving bandwidth (sending only the important events instead of the full video).

But the edge has constraints: small memory, limited compute, battery, varied devices, and difficult updating. The solutions: small models (SDAIA’s guide: fewer than about 5 billion parameters suit phones), quantisation, runtimes specific to each device, and over-the-air updates. The common pattern is hybrid: the device handles the easy cases and sends the hard ones to the server.

Real-World Example

A factory with 200 cameras monitoring the production line for defects. Sending 200 video streams to the cloud is very expensive and slow. The solution: each camera has a small chip running a small model that inspects each piece in fractions of a second, and it sends the cloud only “piece number 4521 is defective” with its image. If the small model is not sure, it sends the image to a larger model on the server.

Key Terms
Edge / on-device AIالطرفي / على الجهاز
Running the model on the device close to the data instead of on the central server.
Neural Processing Unit — NPUوحدة المعالجة العصبية
A chip specialised in neural-network operations, found in modern phones and computers.
Federated learningالتعلم الاتحادي
Improving the model by learning across many devices without collecting their data centrally: each device learns locally and sends only the update.
Over-the-air (OTA) updateالتحديث عن بُعد
Sending a new version of the model to the devices over the network without needing to reach them by hand.
Bandwidthعرض النطاق
The amount of data that can be moved across the network per second.

The hybrid pattern is common: the device handles the common case and escalates the hard cases to a model on the server.

1.7 The three reference architectures

In Plain Terms

Three “ready-made blueprints” cover most scenarios. Real-time scoring service: the request passes through a gateway, then a service fetches the features from a fast store, runs the model together with hard rules, and returns the decision and its reasons. Enterprise RAG assistant: documents are ingested when they change, and the user passes through sign-in, then the model gateway, then permission-filtered search, then the model inside the Kingdom, then the guardrails. Batch scoring pipeline: a nightly job on cheap machines, with quality checks, an alert if it is late, and a fallback (yesterday’s scores).

How to use them: determine the shape from the waiting question. “Someone is waiting” → online. “Documents and questions” → RAG. “Every customer every night” → batch. Then check each component: where is the data? How does it scale? What if it fails? What does it cost?

Real-World Example

Read the first blueprint as a story of a card transaction. The customer pays in a shop → the request passes through a gateway that verifies the shop → the scoring service fetches “the number of card transactions in the last hour” from a fast store in under 5 ms → the model computes the probability of fraud → and fixed rules (“the card is reported stolen” → immediate refusal) → the decision is returned with the reason → and the transaction is logged for future models to learn from.

Key Terms
Reference architectureالمعمارية المرجعية
A proven standard design for a particular type of system, used as a starting point and adapted to each case.
Rules engineمحرك القواعد
A component that executes fixed, explicit rules alongside the model, such as “refuse every reported card”.
Key–value storeمفتاح–قيمة
A very fast, simple database: you give it a key (the customer number) and it instantly returns the value linked to it.
Event streamتدفق الأحداث
A channel in which events (every transaction, every decision) are published for other systems to use, such as monitoring and training.

The client passes through the API gateway (authentication and rate limiting) to a stateless scoring service with several replicas across several availability zones. It fetches features from an online feature store (key–value, under 5 ms), and runs the model in-process, alongside a rules engine for hard blocks, then issues the decision with reason codes and publishes an event for monitoring, labels and retraining.

Chapter 2

Hardware, Sizing and LLM Serving

2.1 Hardware fundamentals: why GPUs?

In Plain Terms

You saw in Unit 00 why GPUs excel: thousands of simple workers in parallel. Here is a deeper idea: speed is often set by memory, not by computation. There are memory “layers”: very small and very fast inside the chip, then GPU memory (tens of gigabytes, fast), then server memory (bigger and slower), then the disks, then the network.

When a language model writes a single word, it must read all the weights from GPU memory. So speed here is set by the speed of reading from memory, which is called “memory-bound”. Reading a long question in one go, and training, are limited by the speed of computation. That is why every technique that reduces the data moved (quantisation, FlashAttention, GQA) speeds things up.

Real-World Example

A very skilled cook can chop 100 vegetables a minute, but the fridge is in another room, and he can carry only 10 at a time. His real speed is set by the trips to the fridge, not by his chopping skill. If you gave him smaller pieces (quantisation), he would carry more per trip and become faster. If we put the vegetables in a very distant fridge (offloading the weights to server memory), he becomes much slower.

Key Terms
Memory hierarchyهرمية الذاكرة
The layers of memory from the smallest and fastest (inside the chip) to the largest and slowest (the disks and the network).
High Bandwidth MemoryHBM
The GPU’s main memory: tens of gigabytes with a very high read speed (terabytes per second).
Memory-bound / compute-boundمقيّد بالذاكرة ومقيّد بالحوسبة
Memory-bound: speed is set by the speed of moving data (such as generating words). Compute-bound: it is set by the speed of computation (such as training and reading a long question).
Tera floating-point operations per secondTFLOPS
A trillion arithmetic operations per second. A measure of computing power, and not enough on its own to estimate generation speed.
PCI ExpressPCIe
The ordinary link between the GPU and the rest of the server. Much slower than the dedicated links between GPUs.
High-speed interconnectsNVLink / InfiniBand
NVLink: a very fast link between GPUs inside a single server. InfiniBand: a very fast network between servers.
Tensor Processing UnitTPU
A chip from Google specialised in neural-network operations, an alternative to GPUs.

What the Exam Tests

Neural networks are dominated by large matrix multiplications. GPUs run thousands of simple cores in parallel and include tensor cores specialised in low-precision matrix mathematics (FP16/BF16/FP8/INT8). CPUs, by contrast, have few powerful cores and large caches, and are better for branching logic, classical machine learning, small models and data preparation. Other accelerators — TPUs from Google, and NPUs in phones and computers — follow the same idea: hardware specialised in matrices.

The memory hierarchy sets the speed

registers / on-chip SRAM (tens of MB) → HBM (tens of GB, TB/s) → host RAM (hundreds of GB, via PCIe) → local NVMe → network storage

From the fastest and smallest to the slowest and largest. Token generation in language models is usually limited by how fast the weights and KV cache stream from HBM — that is, it is memory-bound — whereas prompt processing (prefill) and training are compute-bound. This is why bandwidth, and not TFLOPS alone, appears in good comparisons, and why techniques that reduce the bytes moved (quantisation, FlashAttention, GQA) speed up performance. It is also why offloading weights to host memory is slow: host memory is much slower over PCIe.

Interconnects

Inside a server, GPUs communicate over high-bandwidth links (NVLink-class) much faster than PCIe; between servers, over InfiniBand or high-speed Ethernet (RDMA). Tensor parallelism needs the fast links inside a node; data parallelism tolerates slower links between nodes; and a poor interconnect makes multi-GPU training scale badly.

2.5 LLM serving performance techniques

In Plain Terms

Techniques to make LLM serving faster and cheaper. Continuous batching: it brings new requests into the batch whenever one finishes, so nobody waits. PagedAttention: it manages the memory of the conversations efficiently, like the pages of a book. Quantisation: a smaller model. Prefix caching: reusing the fixed part of the prompt. Speculative decoding: a small model proposes words and the large one verifies them. Tensor parallelism: splitting the model across several GPUs. A smaller model: the biggest lever if its quality is enough. A limit on answer length. Routing: the easy ones go to a small model.

The basic trade-off: batching increases throughput, and may slow each request. Note a point the exam asks about: speculative decoding does not change the outputs (it preserves their distribution), whereas switching to a smaller model or heavy quantisation may change them.

Real-World Example

Continuous batching is like an airport shuttle bus passing through stops. The old way: the bus waits until its 40 seats are full and then leaves, and waits until everyone gets off before returning. The continuous way: whenever a passenger gets off at a stop, another boards in their place immediately, so there are no empty seats and no long waiting. speculative decoding: a fast assistant writes a draft of 5 words, and the expert reviews them all at once and accepts the correct ones. The result is as if the expert had written it alone, but faster.

2.6 LLM capacity in tokens, and load tests

In Plain Terms

For language models, measure capacity in tokens per second, not in requests per second, because one request may need 50 words and another 2,000. The calculation: required tokens per second = number of concurrent conversations × the speed of each conversation. Then you divide by what one machine can sustain (from the load test), and add one spare.

Real-World Example

The calculation: 500 users are talking to the assistant at the same moment, and each needs 20 words per second for comfortable reading. Required = 500 × 20 = 10,000 words per second. The load test showed that one machine sustains 2,500 words per second while the time to first word stays under a second. So 10,000 ÷ 2,500 = 4 machines, and +1 spare = 5.

2.7 Capacity planning for an LLM service — a full worked example

In Plain Terms

This is the most important calculation example in the unit, and it brings together everything before it in five steps. (1) Memory: how much do the weights take? How much does each conversation take? How many conversations fit? (2) Throughput: can the machine sustain the writing speed required for all the conversations? (3) Number of machines: conversations at peak ÷ conversations per machine, then +1 and spreading across two zones. (4) Scaling policy: on what do we scale? When? What are the minimum and maximum? (5) Cost: reserved for the permanent load, and on-demand for the peak.

The last lesson is important: the biggest variable in capacity is the prompt length. If the search sends 10 chunks instead of 4, the prompt doubles, so each conversation’s memory doubles, so the number of conversations per machine falls, so you need more machines. Prompt discipline is capacity planning.

Real-World Example

The calculation step by step. Memory: a 48 GB machine. The weights are 8, and the software itself about 6, so 48 − 8 − 6 = 34 GB remains for the conversations. Each conversation: 2,000 tokens × 64 KB ≈ 128 MB. So 34,000 ÷ 128 ≈ 265 conversations in theory, and we plan for 150 as a safety margin. Throughput: 150 conversations × 15 tokens per second = 2,250, and the machine sustains 3,000 ✓. Machines: 300 conversations at peak ÷ 150 = 2 machines, and +1 for spare and spreading = 3.

3.2 Data parallelism and ZeRO/FSDP in detail

In Plain Terms

Data parallelism in detail: after each step, each machine has computed slightly different adjustments because it saw different data. So the machines come together in an operation called all-reduce and take the average of the adjustments, so the model stays identical on all of them. It works well as long as the model fits on one machine.

ZeRO solves the problem of “why does every machine hold a complete copy of everything?”. Three stages: the first splits the optimiser state across the machines, the second splits the gradients as well, and the third (also called FSDP) splits the weights themselves, so each machine holds a part and fetches the rest when needed. So the memory per machine falls roughly by the number of machines, in exchange for more communication between them.

Real-World Example

Four students solving an exercise book together. Ordinary data parallelism: each has a complete copy of the book and all the notes, and solves a different chapter, then they exchange what they learned. This wastes paper. ZeRO stage 3: the book is divided into 4 parts, each student carries only a quarter of it, and when one needs a page from another quarter, he asks his colleague for it. Far less paper, and more exchange.

3.5 Scaling an LLM service on Kubernetes — what actually limits you

In Plain Terms

A very frequent trap in the exam. The language-model server runs on a GPU, and its CPU stays almost idle even while it is under full pressure. So if autoscaling is set to “add a replica when CPU reaches 70%”, it will never add anything, while the queue grows and users wait.

The fix: change the scaling metric to the number of requests in progress or the queue length. Not “a bigger machine”, and not “lowering the CPU threshold”. Remember also that adding a new GPU server may take minutes, and loading the model several more. So keep a permanent margin, scale ahead of known peaks, and keep the model locally on the servers.

Real-World Example

The scenario: GPU utilisation 98%, a queue with hundreds of requests, and response time rising, while CPU is at 25%, so scaling adds no replicas. It is as if a restaurant manager decided the number of chefs by “how much the cashier talks” instead of “how many orders are waiting in the kitchen”. The cashier is calm and the kitchen is swamped. The wrong metric gives a wrong decision.

What the Exam Tests

  • Headroom (permanent spare capacity).
  • Scheduled pre-scaling for known peaks.
  • Local model caches on the nodes.
  • Queue-based buffering so that short bursts wait briefly instead of failing.
Scale on in-flight requests or queue depth, not on CPU — a GPU-bound server’s CPU utilisation stays low while it is saturated.

The usual question pattern: GPU utilisation at 98%, a queue in the hundreds, and time to first token rising, while CPU is at 25% so HPA adds no replicas. The fix is to change the scaling metric to a custom one (concurrency or queue depth via HPA or KEDA) — not a bigger GPU and not lowering the CPU target.

3.6 Storage, vector databases and data platforms

In Plain Terms

Where do we keep the vectors? Up to a few million vectors, and with an existing Postgres database, adding vectors to it (pgvector) is often enough. For very large volume, many requests or complex filtering: a dedicated vector database.

The memory calculation for vectors is easy: count × dimensions × 4 bytes. If the result is large there are two levers: vector quantisation (cuts 4 to 32 times) or reducing the dimensions. The other places to store things: object storage for large files, the lake for raw data, and the warehouse for analytics.

Real-World Example

The calculation: 10 million chunks, each chunk a vector of 1,024 numbers, and each number 4 bytes. 10,000,000 × 1,024 × 4 = 40,960,000,000 bytes ≈ 41 GB, and that is before counting the index itself. If we reduced the dimensions to 512 it would be half (≈ 20 GB). If we quantised each number to one byte instead of 4, it would be a quarter (≈ 10 GB).

3.7 Tuning and scaling vector indexes

In Plain Terms

Vector indexes have tuning dials. In HNSW: M (the number of links per point) and efSearch (how wide the search is). In IVF: nprobe (how many groups we search). The rule: higher → more accuracy, and more slowness and memory. The right method: measure accuracy on a sample against the full search, and choose the lowest value that meets the target.

Three notes. Very selective filtering (for one small tenant) can weaken approximate search; the fix is indexes that support filtering, or an index per tenant. Sharding increases capacity, and replication increases requests and availability. heavy deletion can weaken some indexes, so they need periodic rebuilding, and deletion is necessary for the Personal Data Protection Law (PDPL).

Real-World Example

Looking for a book in a huge library. Low efSearch: you check only two nearby shelves, fast but you may miss the book. High efSearch: you check twenty shelves, slower but you usually find it. The skill: try it on 100 books whose places you know, and choose the smallest number of shelves that finds 95% of them. sharding versus replication: sharding is a library divided across 3 buildings (it holds more books), and replication is 3 identical copies of the library (it serves more visitors, and if one is closed two remain).

4.1 Network and latency budgets

In Plain Terms

Every trip across the network takes time, and the time grows with distance. Inside the machine itself: microseconds. In the same zone: under a millisecond. Between the zones of a single region: 1–2 milliseconds. Between continents: tens to over 100 milliseconds.

So if your whole budget is 50 milliseconds (like a fraud decision), the request cannot go to another continent and come back. This makes hosting inside the Kingdom a performance decision too, not only a compliance decision, for users in Saudi Arabia. The tips: keep services that talk to each other in the same place, reuse connections, and put the feature store beside the model.

Real-World Example

You need a paper from a colleague. If he is at the next desk, seconds. If he is on the fifth floor, two minutes. If he is at the company’s branch in another city, a whole day by post. If you needed 10 papers from him for every decision, his being in another city makes the work impossible however fast you are.

The time a request takes to reach the other end and the reply to return.

Keeping a set of open connections ready and reusing them, instead of opening a new connection for every request.
Keep-aliveإبقاء الاتصال حيًّا
Keeping the network connection open after the request so that it can be used for later requests, which saves the time of opening a new connection.
Co-locationالتجاور
Placing services that communicate a lot in the same place (the same zone) to reduce network time.

In Plain Terms

The rule: diagnose from the trace first. A bigger machine does not cure queue waiting, nor long network trips, nor long prompts. An important point: perceived time (when the user sees something) differs from actual time (when the answer is complete). Streaming, showing sources first, and a progress indicator improve the perceived time at no cost.

Real-World Example

A patient complains of a long wait at the hospital: 3 hours. By tracing: registration 10 minutes, waiting before the doctor 2.5 hours, the examination 15 minutes, and the pharmacy 5 minutes. Hiring a cleverer doctor (a stronger machine) will not solve the problem, since the examination is only 15 minutes. The problem is in the queue, and the fix is more doctors in peak hours or organised appointments.

4.3 Performance engineering for classical models

In Plain Terms

Classical models (boosted trees and linear models) are very fast by nature: a few milliseconds on an ordinary processor. If the service is slow, the cause is usually not the model, but feature retrieval: slow database queries before the model starts.

The remedies: compute the features in advance and keep them in a fast store, batch the queries, export the model to a fast runtime format, avoid slow Python in the critical path, group requests close in time into small batches, and if all the inputs are known in advance, compute all the results in advance and read them from a table.

Real-World Example

A model computes the result in 2 ms, but before it there are 40 ms of database queries to fetch “the customer’s average spending”, “the number of their transactions” and “the age of their account”. The total is 42 ms, 95% of it in the data. Speeding up the model itself will change almost nothing. Computing these features in advance and keeping them in a key–value store makes fetching them take under one millisecond.

Key Terms
Critical pathالمسار الحرج
The chain of steps that must complete before replying to the user. Any slowness in it slows the reply directly.
Micro-batchingالتجميع المصغّر
Gathering the requests that arrive within a few milliseconds and processing them together, with a maximum wait.
Oversubscriptionالإفراط في الاشتراك
Running more processes or threads than the processor’s cores can handle, so they crowd each other and slow each other down.

What the Exam Tests

Classical models (boosted trees, linear models and small networks) usually meet millisecond budgets on CPUs when they are well engineered:

  • Feature retrieval dominates: a model that takes 2 ms behind 40 ms of database queries is slow because of the data, not the model. Pre-compute the features, use an online feature store (key–value lookup), batch the queries, and cache the stable features.
  • Optimised runtimes: export to ONNX or use native compiled predictors (Treelite-style for trees); and avoid Python overhead on every request in the critical path.
  • Micro-batching: for throughput, group the requests that arrive within a few milliseconds, with a cap on the wait time so that latency stays within the target.
  • Model size: fewer and shallower trees, or distilled models, when the budget is tight; and measure the cost of that in accuracy.
  • Concurrency: several worker processes per node; pin threads; avoid oversubscription.
  • Pre-computation: if the inputs are known (all customers, all products), score in batch and serve the results by lookup — under 1 ms at any scale.

4.4 Caching layers end to end

In Plain Terms

Caching can sit in many layers: at the user, the API, the semantic, the search, the embeddings, the prefix and the features. Each layer has what it keeps, when it is invalidated, and its risk.

The most important rule: the cache key must include everything that changes the answer: the user’s or tenant’s permissions, the language, the model version, the prompt version and the index version. A cache shared between different permissions is a leakage vulnerability, not an optimisation. For prefix caching: the fixed part first, because any change at the start, even today’s date, invalidates the cache.

Real-World Example

The cache key: the question “what is my leave balance?” from different employees has different answers. If the key were only “the question text”, the second employee would get the first one’s balance! The right key: (question text + user identity + …). prefix caching: a prompt that starts with “Today: 2026-11-02. You are an assistant…”. The date changes every day so the start of the prompt differs, so the caching never works. Move the date to the end of the prompt.

4.5 Cloud cost engineering (FinOps)

In Plain Terms

FinOps is managing cloud cost with discipline. Pricing types: on-demand (flexible and more expensive) for peaks, reserved (a commitment with a large discount) for the permanent minimum, Spot (very cheap and may be reclaimed) for interruptible work, and serverless for rare traffic. unit economics: express the cost per useful outcome (per resolved conversation, or per processed document), not per request. An important signal: a bill that grows while traffic is flat = one of the hidden lines.

Real-World Example

Model “A” costs 100 riyals per 1,000 conversations and resolves 90% of them. Model “B” is 30% cheaper (70 riyals) but resolves only 80%. 4.6 Energy and sustainability

In Plain Terms

Energy is not only a cost issue. The “Social and Environmental Benefits” principle in SDAIA’s principles, and the environmental impacts category in the national risk framework (energy consumption and carbon footprint), make efficiency a governance topic as well.

The levers are the same as the cost levers: the smallest model that suffices, quantisation and distillation, efficient batching, avoiding unnecessary retraining, scheduling flexible training when the energy is cleaner (within the residency constraints), measuring energy, and reusing ready-made models instead of training from scratch.

Real-World Example

A team wants to train a huge model “because it is the latest” for a simple classification task that a small model would handle. The argument against is twofold: cost (weeks of expensive GPUs) and ethics (large energy consumption with no notable added benefit, contrary to the spirit of the environmental-benefits principle). Like running central air conditioning for a whole building to cool a single room.

The Scenario

Solution Steps

  1.     Explanation

    The need is seconds-to-minutes freshness over windows of an event stream — the streaming/near-real-time mode. A stream processor (Kafka + Flink-type) aggregates each sensor's 30-second window and scores it with the small model, meeting the one-minute target at about 8,000 readings/s (40,000 ÷ 5). Synchronous per-reading calls couple low-power sensors to model availability and do not build windows; on-device scoring is ruled out by the hardware; hourly batch still misses the one-minute target.

  2. 2Interconnect and tensor parallelism placementHard

    A national research lab trains a 30B model on two servers, each with 8 GPUs connected internally by NVLink; the servers are joined by 25 Gb/s Ethernet. The job uses tensor parallelism of degree 16 spanning both servers. Throughput is barely higher than on one server, and profiling shows GPUs idle most of each step waiting for communication. What change is most likely to fix the scaling?

    Explanation

    Tensor parallelism exchanges activations inside every layer, so it needs very fast intra-node links such as NVLink; stretching it over 25 Gb/s Ethernet makes GPUs wait. Data parallelism (or pipeline parallelism) communicates far less often and tolerates slower inter-node links. Keep TP = 8 within each server and use DP = 2 across servers. A third server on the same layout adds even more slow-link traffic.

  3. 3Scheduled pre-scaling for known peaksHard

    A bank's Arabic chat assistant sees traffic triple every month on salary day between 9 and 11 am. Metric-based autoscaling works, but a new GPU node takes about 8 minutes to join and the model another 4 minutes to load, so for roughly the first 15 minutes of each peak users get errors and timeouts. Off-peak cost must stay low. What should the team add?

    Explanation

    The peak is predictable and the scale-out path takes about 12 minutes (8 + 4), so any reactive metric fires too late. Scheduled scaling pre-warms capacity before the known peak, metric-based autoscaling handles the rest, and a short queue lets brief bursts wait instead of failing. A permanent 3× fleet meets the peak but wastes money the rest of the month.

  4. 4Autoscaling signal for GPU inferenceHard

    A telecom operator serves an Arabic support LLM on Kubernetes. The Horizontal Pod Autoscaler targets 70% CPU. During the evening peak, GPU utilisation sits at 98%, the request queue in each pod grows to hundreds, and p95 time-to-first-token climbs from 0.9 s to 7 s — yet pod CPU stays around 25%, so the HPA never adds replicas. The GPU node pool has two idle nodes available. What should the team change first?

    Explanation

    Root cause: the autoscaler watches the wrong signal. A GPU-bound model server is saturated while its CPU stays low, so a CPU target never fires. Scale on a metric that tracks real load — concurrent/in-flight requests or queue depth (HPA custom metrics or KEDA). Idle GPU nodes already exist, so node supply is not the bottleneck; a 20% CPU target would scale on noise rather than load, and a bigger GPU is the costly vertical reflex.

  5. 5Fitting weights plus KV cache on a GPUHard

    A health insurer will self-host a 32B-parameter model for claim-note drafting. It must serve 40 concurrent sessions of up to 4,096 tokens each; for this model the KV cache, kept in FP16, needs about 0.25 MB per token. Arabic evaluation showed INT8 weights with no measurable quality loss, while INT4 fell below the acceptance threshold. Ignoring a small runtime overhead, which is the cheapest configuration that fits?

    Explanation

    Memory is the hard filter. KV cache = 40 × 4,096 × 0.25 MB = 40,960 MB ≈ 40 GB. Weights: FP16 = 32 × 2 = 64 GB; INT8 = 32 GB; INT4 = 16 GB. Totals: FP16 ≈ 104 GB (needs two cards), INT8 ≈ 72 GB (fits one 80 GB card), INT4 ≈ 56 GB (does not fit 48 GB and fails quality anyway). INT8 on one 80 GB GPU is the cheapest option that fits and meets quality.

  6. 6Static vs continuous batchingHard

    An e-government chat service uses a basic inference server with static batching: it waits until 16 requests arrive or 500 ms pass, then runs the batch until the longest answer finishes. Short answers wait for long ones, KV-cache memory is pre-allocated for the maximum length and shows heavy fragmentation, and at peak the queue grows while GPU utilisation averages only 45%. Budget for new hardware is frozen this year. What is the most effective change?

    Explanation

    The symptoms point to the serving software, not the hardware: static batches hold short requests hostage to the longest one, and max-length KV pre-allocation wastes memory and caps concurrency. Continuous (in-flight) batching admits and retires requests at every decode step, and PagedAttention-style KV paging removes fragmentation, giving a large throughput gain on the same GPUs — vLLM, TGI and TensorRT-LLM provide both.

  7. 7Index degradation after heavy deletesHard

    A telecom's customer-history RAG index processes thousands of PDPL deletion requests and contract expiries every week. Over six months, recall@10 measured against exact search has fallen from 0.95 to 0.86, query latency has crept up, and index memory has not shrunk even though about 30% of the vectors were deleted. Embedding model and query mix are unchanged. What is the most appropriate action?

    Explanation

    Some ANN indexes degrade under heavy deletes: removed items linger as tombstones, the graph loses good links, recall drops and memory does not shrink. The memo's remedy is periodic rebuilds, verified by recall@k against exact search. Nothing in the embedding model changed, so retraining is the reflex; doubling efSearch buys recall back with more latency; leaving deleted personal data in the index fails PDPL deletion obligations.

  8. 8Vector extension vs dedicated vector DBHard

    A government agency's policy assistant indexes about 1.5 million chunks and expects slow growth to roughly 3 million over three years. Query load is about 15 queries/s with simple department filters, and the p95 search target is 80 ms. The agency already runs a well-managed in-Kingdom Postgres cluster, and its two-person team has no spare capacity for new platforms. An architect proposes a dedicated three-node vector database cluster. What is the best decision?

    Explanation

    Up to a few million vectors with an existing Postgres and simple operations, a vector extension is often enough; a dedicated vector DB pays off at very large scale, high QPS or advanced filtering. Here scale (≤ 3M), load (15 q/s) and filters are modest, and the team constraint favours no new platform. A dedicated cluster or early sharding is over-engineering; a flat in-memory index scans every vector and lacks the database's persistence and operations.

  9. 9Managed API vs self-hosting under uncertaintyHard

    A university wants a GenAI assistant that answers questions about its published course catalogue and public admission rules — all data is classified Public and contains no personal data. The IT team has three engineers and no GPU or Kubernetes experience, demand is unknown (anything from 50 to 5,000 users a day), and the launch must happen in six weeks for the admission season. Which hosting approach is most appropriate?

    Explanation

    Small team, uncertain demand and a short deadline point to a managed service: no operations burden, the fastest start and pay-per-token cost that tracks actual usage. Because the data is Public with no personal data, the usual residency watch-out does not block a managed API. Self-hosting wins only at high, steady volume with a team able to run it; long commitments make no sense when demand is unknown.

  10. 10Sharded data parallelism for full fine-tuningHard

    A research centre has decided on full-parameter fine-tuning of a 13B model on one server with 8 × 80 GB GPUs linked by NVLink. With mixed-precision Adam, weights, gradients and optimiser states take about 16 bytes per parameter. Their DDP script fails with out-of-memory on every GPU before the first step, even at micro-batch size 1. What change addresses the root cause?

    Explanation

    Training state ≈ 13B × 16 bytes ≈ 208 GB, and DDP keeps a full copy on every GPU, so it can never fit in 80 GB whatever the batch size. ZeRO-3/FSDP shards parameters, gradients and optimiser states, cutting per-GPU state to about 208 ÷ 8 ≈ 26 GB plus activations, over the fast NVLink links already available. Accumulation and checkpointing only reduce activation memory; more DDP nodes still replicate everything.
